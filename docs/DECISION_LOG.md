# Decision Log: go-ozon-marketplace

**Версия:** 0.3.0  
**Дата обновления:** 2026-06-11

Ключевые архитектурные решения и их обоснование. Каждое решение — 1–2 абзаца.

---

## 1. Почему Saga Orchestrator, а не Choreography

**Решение:** `order-service` выступает централизованным оркестратором Saga. Он последовательно вызывает `inventory-service.Reserve` → `payment-service.ProcessPayment` и при необходимости инициирует компенсацию.

**Обоснование:** В маркетплейсе критически важен строгий порядок шагов: нельзя списать деньги до резервирования товара. Orchestrator даёт явный контроль над порядком, состоянием и компенсацией в одном месте. Choreography требовала бы, чтобы каждый сервис сам решал, когда и что компенсировать — это сложнее отлаживать и тестировать. Дополнительно recovery worker в оркестраторе позволяет доисполнять прерванные саги после рестарта сервиса, что в choreography потребовало бы распределённого отслеживания состояния.

## 2. Почему GraphQL + gRPC, а не REST

**Решение:** Клиенты ходят в `api-gateway` через GraphQL (HTTP), а межсервисное взаимодействие — через gRPC.

**Обоснование:** GraphQL позволяет фронтенду запрашивать ровно те поля, которые нужны, и объединять несколько сущностей в один запрос — это снижает количество round-trip'ов для сложных страниц (карточка товара + отзывы + рекомендации). gRPC между сервисами даёт строгий контракт (proto), высокую производительность (HTTP/2 + binary protobuf) и встроенную поддержку streaming, deadlines и interceptors. REST не давал бы ни type safety на границах, ни автоматической генерации клиентов/серверов.

---

## 3. Почему Kafka + Outbox, а не direct gRPC для async

**Решение:** При записи в БД одновременно атомарно пишем событие в `outbox` таблицу. Отдельный relay-процесс читает outbox и публикует в Kafka. Analytics и notifications читают из Kafka.

**Обоснование:** Direct gRPC вызовы для асинхронных событий нарушают атомарность: если БД записала заказ, а вызов в notification-service упал — система в неконсистентном состоянии. Outbox pattern гарантирует, что событие будет опубликовано ровно один раз (если транзакция коммитнулась). Kafka выбран как промышленный брокер с персистентностью, поддержкой consumer groups и DLQ. Redpanda используется в development для упрощения локальной инфраструктуры (один бинарник, совместимость с Kafka API).

## 4. Почему ClickHouse, а не PostgreSQL для аналитики

**Решение:** События заказов пишутся в ClickHouse через batch insert. Дашборды и отчёты строятся из ClickHouse.

**Обоснование:** PostgreSQL — OLTP-система, оптимизированная для транзакционных нагрузок. Аналитические запросы (агрегации по миллионам строк, временные окна, группировки) создавали бы table scans и нагружали primary БД. ClickHouse — колоночная OLAP-СУБД, специально спроектированная для аналитики: векторизованное выполнение, сжатие данных, партиционирование по времени (`toYYYYMM`), TTL для старых данных. Переход на ClickHouse позволил отделить аналитическую нагрузку от операционной.

## 5. Почему Helm + ArgoCD, а не raw Kubernetes

**Решение:** Каждый сервис упакован в Helm chart. ArgoCD управляет деплоем из Git в Kubernetes. Flagger управляет canary-релизами.

**Обоснование:** Raw Kubernetes манифесты быстро становятся неуправляемыми при росте числа сервисов: дублирование конфигураций, отсутствие параметризации (staging vs production), сложность rollback. Helm даёт templating, values-файлы и версионирование релизов. ArgoCD добавляет GitOps: единый источник правды в Git, автоматическую синхронизацию, drift detection и self-healing. Flagger автоматизирует canary-деплой с метриками из Prometheus, снижая риск выкладки багов в production.

## 6. Почему Circuit Breaker + Rate Limiting

**Решение:** `api-gateway` защищён двумя механизмами: rate limiter (sliding window в Redis) и circuit breaker (in-memory state machine).

**Обоснование:** Rate limiting решает проблему «шумного соседа» — предотвращает исчерпание ресурсов одним клиентом или ботом. Разделение по ролям (user/admin/service) позволяет дать админам и внутренним сервисам большие квоты без угрозы для публичного API. Circuit breaker решает проблему каскадных отказов: если `payment-service` начал таймаутить, gateway быстро отказывает запросы, не дожидаясь истечения TCP-таймаутов, и даёт сервису время на восстановление. Вместе они обеспечивают graceful degradation под нагрузкой.

---

## 7. Почему Feature flags в Redis (запланировано)

**Решение:** Архитектура feature flags предполагает Redis-backed storage с in-memory LRU-кэшем на стороне сервисов.

**Обоснование:** Feature flags требуют низкой латентности (проверка на каждый запрос) и высокой доступности. Redis даёт sub-millisecond чтение и pub/sub для мгновенной инвалидации. In-memory кэш на стороне сервиса защищает от сетевых задержек и делает флаги доступными даже при кратковременных проблемах с Redis. Альтернатива — централизованный сервис фиче-флагов (LaunchDarkly, Unleash) — добавляет сетевой хоп и внешнюю зависимость. Локальное решение на Redis проще эксплуатировать в self-hosted инфраструктуре и не требует дополнительных контрактов.

> **Статус:** Feature flag engine не реализован в v0.3.0. Решение зафиксировано для будущей реализации.
